MachineLearningForecast.jl

Generic, composable time-series forecasting built on the MLJ model interface: any MLJ Deterministic regressor is a valid base model.

using MachineLearningForecast, EvoTrees, Dates

df = (ds = collect(Date(2020,1,1):Day(1):Date(2023,12,31)),
      y  = randn(1461) .+ 10)

fc = Forecaster(EvoTreeRegressor(nrounds=200, eta=0.05);
                features = FeatureSet(Lag(1), Lag(7), RollingMean(7),
                                      Calendar(:dayofweek), Fourier(365.25, 3)),
                strategy = Recursive(),
                freq     = Day(1))

fitted = fit(fc, df)
fcast  = forecast(fitted, 28)

MachineLearningForecast is Tables.jl-native: any Tables.jl-compatible source is accepted (NamedTuple of vectors, DataFrame, CSV.File, ...), and all tabular results are columntables (NamedTuples of vectors).

See the README for the full tour: feature catalogue, strategies, backtesting, and the two-level tuning story — including the leakage warning about preferring TimeSeriesCV to MLJ's CV() when tuning base models with MLJ's TunedModel.

Leakage and conventions states what the package guarantees against leakage, the conventions behind forecasts and backtest scores, how to choose a strategy, and recipes for custom features. Using different models compares six MLJ learners on the M3 monthly series. Tuning the models tunes their hyperparameters on a validation window.

API reference

MachineLearningForecast — Module
MachineLearningForecast

A generic, composable time-series forecasting package built on the MLJ model interface: any MLJ Deterministic regressor is a valid base model, and a Probabilistic one forecasts its predicted mean.

  • Declarative feature engineering: FeatureSet, Lag, RollingMean, RollingStd, RollingMin, RollingMax, Diff, Calendar, Fourier, Exogenous, CustomFeature.
  • Pluggable strategies: Recursive, Direct.
  • Target transforms, fitted per series and undone on the forecasts: NoTransform, MeanScale, LastScale, Deseasonalize, LogRatio, Difference, TransformChain; your own subtype TargetTransform implements fit_transform, untransform and, if it shortens the series, dropped_rows (public, not exported: import MachineLearningForecast: fit_transform, untransform, dropped_rows).
  • Panel (multi-series) forecasting: set id on Forecaster to fit one global model across many series (nseries, SeriesState).
  • fit / forecast as a functional pair; backtest for expanding-window cross-validation; tune for pipeline tuning with an extensible ask!/tell! TuningStrategy interface.
  • Metrics: mae, rmse, mape, smape, mase, rmsse.

Forecasting

MachineLearningForecast.Forecaster — Type
Forecaster(model; features, strategy=Recursive(), freq, target=:y, time=:ds, id=nothing,
           transform=NoTransform())

Immutable forecasting specification.

  • model: any MLJ Deterministic regressor instance (EvoTrees, DecisionTree, XGBoost, linear models, ... — anything implementing the MLJ model interface), or a Probabilistic one, whose predicted mean is the forecast. Used as a prototype; fit never mutates it.
  • features: a FeatureSet describing the design matrix.
  • strategy: a ForecastStrategy — Recursive (default) or Direct.
  • freq: the series frequency as a positive Dates.Period, e.g. Day(1), Month(1); a sum such as Day(1) + Hour(1) is not accepted.
  • target: name of the target column (default :y).
  • time: name of the time column (default :ds), of a type supporting + with freq (Date, DateTime).
  • id: name of the series-id column for panel (multi-series) data, or nothing (the default) for a single series. When set, data is a long-format panel: one row per (series, timestamp). Features are materialised within each series — a lag never reaches across a series boundary — and the rows of every series are then pooled to fit one global model, so short or noisy series borrow strength from the rest. Series may be ragged (different start dates, end dates and lengths); each forecasts forward from its own last timestamp. forecast then returns an id column alongside the timestamps.
  • transform: a TargetTransform applied to each series' target before features are built, e.g. LastScale or TransformChain(LastScale(12), Deseasonalize(12), LogRatio(12)). Its state is fitted per series on the training history only, and forecasts are mapped back to the original scale. The default NoTransform leaves the target as given.

Fit with fit, which returns a FittedForecaster; the spec itself is never mutated.

Example

using MachineLearningForecast, Dates
fc = Forecaster(model;
                features=FeatureSet(Lag(1), Lag(7), Calendar(:dayofweek)),
                strategy=Recursive(), freq=Day(1), target=:y, time=:ds)

# a panel of many series, fitted as one global model
panel = Forecaster(model;
                   features=FeatureSet(Lag(1), Lag(7)),
                   strategy=Recursive(), freq=Day(1),
                   target=:y, time=:ds, id=:unique_id)

MachineLearningForecast.FittedForecaster — Type
FittedForecaster

The result of fit: the immutable spec plus everything needed to forecast — the trained models (one for Recursive, max_horizon for Direct), the training target history (needed to compute lag features at forecast time), the first/last training timestamps, and the stable feature column order. Use with forecast.

fitted.models holds the trained models, each with the trained copy of the spec's model as .model and its MLJ fitresult as .fitresult. fitted.series holds one SeriesState per series. For a single series, fitted.y_history, fitted.t_last, fitted.t_start and fitted.n_train read its one state directly; on a panel they throw an ArgumentError pointing at fitted.series.

Example

fitted = fit(fc, df)
fitted.models        # the trained model(s)
fitted.series        # one SeriesState per series
fitted.t_last        # single series only: the last training timestamp
forecast(fitted, 28)

MachineLearningForecast.SeriesState — Type
SeriesState

Everything forecast needs about one series: its id (nothing for a single-series forecaster), the training target history that lag and rolling features are computed from, the first and last training timestamps, and the number of training rows. z_history is the history after the spec's TargetTransform, which lag and rolling features and the step index use, and transform_state is what untransform needs; without a transform, z_history is y_history. step0 is the context's step index (ctx.step, see FeatureContext) of the first z_history value: 0 for a single series, and in a panel the steps from the earliest usable series' first (transformed) timestamp.

Read them off a fitted panel forecaster via f.series; for a single-series forecaster the same values are reachable directly as f.y_history, f.t_last, f.t_start and f.n_train.

Example

f = fit(panel_spec, panel)
for st in f.series
    println(st.id, ": ", st.n_train, " rows ending ", st.t_last)
end

nseries(f::FittedForecaster) -> Int

MachineLearningForecast.fit — Function
fit(fc::Forecaster, data) -> FittedForecaster

Fit the forecaster on data, any Tables.jl-compatible table containing the spec's time and target columns (plus any exogenous columns, and the id column for a panel). For a single series the time column must be sorted, duplicate-free, and gap-free with respect to fc.freq. For a panel, rows may come in any order: fit sorts each series by time, and each series must be duplicate-free and gap-free.

fit is a function owned by MachineLearningForecast (not an extension of MLJBase.fit or StatsAPI.fit); qualify as MachineLearningForecast.fit when another fit is in scope.

Example

fitted = fit(fc, df)
fcast  = forecast(fitted, 28)

MachineLearningForecast.forecast — Function
forecast(f::FittedForecaster, h::Integer; future=nothing) -> NamedTuple

Forecast h steps past the end of the training data. Returns a columntable (NamedTuple of vectors) with the spec's time column (the future timestamps t_last + freq, ..., t_last + h*freq) and :y_hat (the point forecasts). Being a columntable, the result is Tables.jl-compatible — pass it to DataFrame, CSV.write, etc. as-is.

If the feature set contains any Exogenous feature, future is required: a table with the time column and every exogenous column, covering all h future timestamps (extra rows are ignored). Without exogenous features, future must be omitted (it is ignored with a warning otherwise).

For a panel forecaster (one with id set), the result also has the id column, before the time column: h rows per series, each series forecast from its own last training timestamp. future must then carry the id column too and cover every series at each of its h future timestamps.

Example

fcast = forecast(fitted, 28)
fcast = forecast(fitted, 28; future=future_exog)   # with Exogenous features
fcast.y_hat                                        # the point forecasts

MachineLearningForecast.Recursive — Type
Recursive()

One model; forecasts are fed back as pseudo-history to compute lag features. The model is trained once on the one-step-ahead frame and iterated over the horizon, so any horizon can be forecast. Neither strategy is better in general: Recursive estimates one model efficiently but is biased when the one-step model is misspecified, and the errors it feeds back accumulate (references under Direct).

Example

using Dates
Forecaster(model; features=FeatureSet(Lag(1)), strategy=Recursive(), freq=Day(1))
source
MachineLearningForecast.Direct — Type
Direct(max_horizon)

One model per horizon step 1..max_horizon. max_horizon fixes the number of models at fit time; forecasting beyond it errors (refit with a larger horizon or use Recursive). On a panel, a series with fewer than max_horizon training rows trains only the step models it has rows for, and fit warns.

Neither strategy is better in general. Recursive estimates one model efficiently but is biased when the one-step model is misspecified, and the errors it feeds back accumulate. Direct is more robust to such misspecification and to non-stationarity such as unit roots, and feeds nothing back, but estimates each horizon separately, which costs variance, and its forecasts at neighbouring steps need not be coherent (Marcellino, Stock & Watson 2006; Chevillon 2007; Ben Taieb et al. 2012). Empirically, iterated (Recursive) forecasts are often at least as accurate on stationary data (Marcellino, Stock & Watson 2006). Compare both with backtest.

At forecast time, the direct models condition their target-history features on the history up to the forecast origin, while exogenous and time features vary per step.

Under Direct, Lag(k) counts back from the forecast origin, so at horizon h it is y[t0-k+1] (t0 is the index of the last observed value), not y[target-k]; Lag(m) is in phase with the target only when h = 1 (mod m); use Lag.(1:m), which holds an in-phase lag at every h, or Recursive.

Model i predicts the target i steps ahead. At fit time its AtOrigin features (lags, rolling statistics, differences, custom) come from the feature row j, and its AtTarget features (time and exogenous) come from the target row j+i-1, which is what forecast feeds at step i; see anchor. Taking both from row j would be a train/serve skew that silently degrades every step after the first.

Example

using Dates
Forecaster(model; features=FeatureSet(Lag(1)), strategy=Direct(28), freq=Day(1))

MachineLearningForecast.inputcolumns — Function
inputcolumns(f) -> Vector{Symbol}

The user columns the feature f reads. forecast and backtest pick exactly these columns from future (or from the held-out rows), and training reads them from the training data too, so they must be present there: fit throws otherwise (unless the feature overrides materialize!). MachineLearningForecast.FeatureContext — Type
FeatureContext(y, t, step, exog)

The row a feature is asked about, passed to featurevalues!. It is read-only: do not keep a reference to it or to y.

  • y: the target history strictly before the row's target (a Vector when forecasting, a view in training). It is empty at the first row when minhistory(f) == 0.
  • t: the timestamp of the row's target.
  • step: the 0-based step index of the row's target. It counts freq steps from the first (transformed) training timestamp, and from the earliest usable series' first (transformed) timestamp on a panel.
  • exog: a NamedTuple of the user columns at the row (it may hold more than inputcolumns(f) when forecasting, so index it by name). When inputcolumns(f) is empty it may be nothing or a NamedTuple (forecasting with another exogenous feature): do not read it then.

Example

using Dates
ctx = MachineLearningForecast.FeatureContext([1.0, 2.0, 3.0], Date(2022, 1, 4), 3, nothing)
ctx.y[end]   # 3.0

MachineLearningForecast.featurevalues! — Function
featurevalues!(out, f, ctx)

Write the values of feature f for the row that the FeatureContext ctx describes into out, a Vector{Float64} of length(outputnames(f)) entries (write every one of them); the return value is ignored. This is the one method a feature must implement for its values: training, forecast and backtest all call it, so by default (unless the feature overrides materialize!) they cannot disagree.

Example

import MachineLearningForecast: outputnames, minhistory, featurevalues!

struct LastTwo <: MachineLearningForecast.TargetFeature end
outputnames(::LastTwo) = [:last_two]
minhistory(::LastTwo) = 2
featurevalues!(out, ::LastTwo, ctx) = (out[1] = ctx.y[end] + ctx.y[end-1]; nothing)

MachineLearningForecast.materialize! — Function
materialize!(out, f, s::TrainingSeries)

Push the training columns of feature f over the series s onto out (a vector of name => column pairs), with missing in the first minhistory(f) rows. The default calls featurevalues! for every row from minhistory(f) + 1 on, so a feature gets this for free; it leaves a row missing when one of its inputcolumns is missing there. Define a method only for speed or to validate a column before any row is read, as Calendar, Fourier and Exogenous do.

Example

using MachineLearningForecast
using MachineLearningForecast: ColumnAccumulator, TrainingSeries, materialize!
out = ColumnAccumulator()
materialize!(out, Lag(1), TrainingSeries([1.0, 2.0, 3.0], 1:3, (;), 0))
out   # [:y_lag_1 => [missing, 1.0, 2.0]]

MachineLearningForecast.anchor — Function
anchor(f) -> Anchor

Which row the columns of feature f describe, AtOrigin or AtTarget. Direct fitting needs it: model i pairs the target i steps ahead with the AtOrigin columns of the feature row and with the AtTarget columns of the target row, which is what forecast feeds. A TargetFeature is AtOrigin; a TimeFeature or an ExogenousFeature is AtTarget. A feature of any other kind must define it, otherwise an ArgumentError is thrown when Direct fits.

An AtOrigin feature may read only ctx.y: its training value comes from the feature row and its forecast value from the origin, while ctx.t, ctx.step and ctx.exog describe the context's row (the feature row in training, the target row when forecasting), so reading them would train on one thing and serve another. An AtTarget feature should not read ctx.y: under Direct it is trained on history up to the target row but served the history at the forecast origin. A feature that reads ctx.t, ctx.step or ctx.exog and not ctx.y is AtTarget: subtype TimeFeature or ExogenousFeature, or define anchor(f) = AtTarget(); one that reads both is correct only under Recursive.

Example

anchor(Lag(1))             # AtOrigin()
anchor(Calendar(:month))   # AtTarget()
source

MachineLearningForecast.Fourier — Type
Fourier(period, order)

Fourier seasonal terms sin(2πkn/period), cos(2πkn/period) for k = 1:order, where n is an integer step index (0-based from the first (transformed) training timestamp, incremented by 1 per freq step). The index continues seamlessly into the forecast horizon, so there is no phase jump at the train/forecast boundary. In a panel, n counts from the earliest usable series' first (transformed) training timestamp, so every series has the same Fourier values on the same date.

period is expressed in units of freq steps, e.g. 365.25 for annual seasonality with daily data. order K produces 2K columns (fourier_<period>_sin_1..K, then fourier_<period>_cos_1..K).

Example

Fourier(365.25, 3)   # annual seasonality, 3 harmonics, for daily data
Fourier(7, 2)        # weekly seasonality, 2 harmonics, for daily data

MachineLearningForecast.Exogenous — Type
Exogenous(cols::Symbol...)

Pass-through of user-supplied covariate columns that are known in the future (e.g. promotions, prices, holidays). At forecast time these columns must be supplied for the full horizon via the future keyword; in backtest they are sliced from the held-out data automatically. Exogenous columns must be numeric (Real or Bool). missing and ±Inf throw an ArgumentError.

NaN is passed to the model unchanged. Learners built for missing values read it as missing: sparsity-aware trees learn a default direction for it (Chen & Guestrin 2016, KDD, §3.4), as does "missing incorporated in attributes" (Twala, Jones & Hand 2008, Pattern Recognition Letters 29(7), 950-956), which Josse et al. (2019, arXiv:1902.06931) recommend over imputation for trees. XGBoost, the system of the first citation, is one such learner. Learners without missing-value handling may treat NaN as an extreme value or refuse it; impute for those.

A backtest uses the realised values of the covariates, so it scores ex-post forecasts (Hyndman & Athanasopoulos 2021, §7.6). For covariates not known at the origin (a competitor's price, the weather) this typically understates the error of the real, ex-ante forecast, which also carries the error of forecasting the covariate. For covariates known in advance (calendar effects, planned promotions, prices you set) ex-ante and ex-post agree. To measure ex-ante error, supply in the held-out rows the covariate values that were available at the origin (a forecast, or a lagged column).

Example

Exogenous(:promo, :price)

MachineLearningForecast.CustomFeature — Type
CustomFeature(name, f, minhistory)

A user-defined target-history feature. f is a function of the target history vector up to and excluding the current row, returning one finite real number (the value of the feature for that row). NaN and ±Inf throw an ArgumentError. minhistory is the minimum number of history values f needs; rows with less history get missing during training and are dropped.

During recursive forecasting, f is called on the growing history vector (actuals followed by earlier predictions), so it sees exactly the same kind of input as during training.

A function that reads anything but its argument, such as a captured series or parent(h), bypasses the leakage guarantee: f must read only the history it is given.

In training f is called once per row on the history before it, so a function that loops over the whole history makes fit O(n^2) in the series length; keep it cheap or use a built-in rolling feature.

Example

using Statistics
# mean of the entire history so far (needs at least 1 observation)
CustomFeature(:hist_mean, mean, 1)
source
MachineLearningForecast.AbstractFeature — Type
AbstractFeature

Root of the feature hierarchy. Concrete features are one of:

  • TargetFeature: computed from the target's history (updated during recursive forecasting), e.g. Lag, RollingMean.
  • TimeFeature: computed from the timestamp only (always computable for future rows), e.g. Calendar, Fourier.
  • ExogenousFeature: passed through from user data (must be provided for the forecast as future), i.e. Exogenous.

Every concrete feature implements three methods:

  • outputnames(f): the names of the columns it produces, a Vector{Symbol}.
  • minhistory(f): the number of history rows it needs before it is defined.
  • featurevalues!(out, f, ctx): writes its values for the one row that the FeatureContext ctx describes.

Training, forecast and backtest all compute a feature through featurevalues!, so by default (unless the feature overrides materialize!) the training columns and the forecast-time values cannot disagree. Optionally a feature defines materialize! (a faster way to fill its training columns), inputcolumns (the user columns it reads; an ExogenousFeature must) and anchor (which row its columns describe under Direct; a feature that subtypes AbstractFeature directly must).

ctx.y holds the target history strictly before the row's target: a TargetFeature never sees the current or a later target value, so rolling and difference features require lag ≥ 1. Under Direct the history is fixed at the forecast origin. An AtOrigin feature (every TargetFeature by default) should read only ctx.y: under Direct its training column comes from the feature row, while ctx.t and ctx.step describe the feature row in training and the target row when forecasting. See anchor.

source

Target transforms

MachineLearningForecast.TargetTransform — Type
TargetTransform

Root of the per-series target transforms. A transform maps one series' training target y to the series z that the model learns and forecasts, and maps the forecasts of z back. Its state is fitted on that series' own training history only, so it never sees the forecast window, and backtest refits it in every fold.

A transform implements two methods and may declare a third, public but not exported, so import them first:

import MachineLearningForecast: fit_transform, untransform, dropped_rows

fit_transform(t, y)        # -> (z, state); z may be shorter, aligned to y's end
untransform(t, ẑ, state)   # -> the forecasts of y for the forecasts ẑ of z
dropped_rows(t)            # -> the rows z is shorter by (optional, default 0)

Features are computed on z, and the first length(y) - length(z) training rows are dropped. Pass a transform as Forecaster(...; transform=...).

Example

fc = Forecaster(model; features=FeatureSet(Lag.(1:12)...), freq=Month(1),
                transform=TransformChain(LastScale(12), Deseasonalize(12),
                                         LogRatio(12)))
source

MachineLearningForecast.dropped_rows — Function
dropped_rows(t::TargetTransform) -> Int

How many rows fit_transform(t, y) removes from the start of a series: z has length(y) - dropped_rows(t) values when y is longer than that. An optional part of the TargetTransform contract, 0 by default. Declare it when your transform shortens the series. fit then checks each series, as the user gave it, against the feature set's history rows plus dropped_rows(t) before it calls fit_transform, so fit_transform never sees a series that is about to be skipped, and a panel skips its short series instead of failing on them. A transform that drops rows without declaring them is checked after it ran, as before. It is not exported, so import it: import MachineLearningForecast: dropped_rows.

Difference(l) drops l rows and LogRatio(w) drops w, as lag-m differencing loses its first m observations; a chain drops the sum of its parts (Box, Jenkins, Reinsel and Ljung 2015, ch. 4).

Example

import MachineLearningForecast: dropped_rows

dropped_rows(Difference(12))                                  # 12
dropped_rows(TransformChain(Difference(1), Difference(12)))   # 13
dropped_rows(LastScale(3))                                    # 0

MachineLearningForecast.Deseasonalize — Type
Deseasonalize(period)

Classical multiplicative seasonal adjustment, applied only to series that pass the M4 competition's seasonality test: the autocorrelation at lag period must exceed its 90% bound, which needs at least 3 * period values. A seasonal series is divided by seasonal indices: centred moving-average ratios averaged by position in the season and normalised to mean 1. The forecasts are multiplied by the index of their own position. Needs positive values when a series is adjusted, and period ≥ 2.

MachineLearningForecast.LogRatio — Type
LogRatio(window)

Model each value as the log of its ratio to the mean of the window values before it, z_t = log(x_t / mean(x[t-window:t-1])), which is scale-free and keeps trending series stationary. The first window values have no ratio and are dropped. Forecasts are rebuilt step by step from the last window training values. Needs positive values and window ≥ 1.

Difference(lag)

Backtesting and metrics

MachineLearningForecast.backtest — Function
backtest(fc::Forecaster, data; horizon, initial=nothing, windows=nothing,
         step=horizon, metrics=(mae, rmse)) -> BacktestResult

Expanding-window time-series cross-validation. Pass exactly one of:

  • initial: train on rows 1:initial, forecast horizon steps, evaluate against the held-out actuals; advance the origin by step rows and repeat while a full horizon of actuals remains.
  • windows: hold out the last windows folds, step apart, the last ending at the end of the data. For a single series this is initial chosen so the final fold ends at the last row.

For a panel forecaster (one with id set), initial cuts folds on the global timestamp grid, since rows are spread across series: initial, step and horizon count distinct timestamps. Each fold trains on every row at or before the origin timestamp, forecasts each series forward from its own last observed timestamp, and scores the result by joining forecasts to actuals on (id, time), so ragged series contribute wherever they have actuals. windows instead counts the folds back from each series' own end, as the M competitions hold out each series' last values: in fold k, every series trains on its rows up to its own cutoff, and one global model is fitted on all of them. If the series are not aligned in calendar time, the training set of a fold can contain values from after another series' cutoff, a known pitfall of global models (Hewamalage, Ackermann & Bergmeir 2023). With initial, all series are cut at the same timestamp, which avoids it. For a panel, the folds table carries the id column too. A fold does not score a series that has no rows up to the fold's origin, too few of them to train on (it is skipped with a warning), or no actuals after it, so the set of scored series can change from fold to fold.

metrics is a tuple of callables (y, ŷ) -> Float64 (e.g. mae, rmse, smape). Scaled metrics that also need the fold's training target — mase, rmsse, or your own, declared via needs_ytrain — are called as metric(y, ŷ; y_train=...) with that fold's training window supplied automatically (on a panel, each series' own, so a scale never mixes series). Unscaled metrics pool the fold's rows; scaled metrics are per series, weighted by scored points; the overall row is the unweighted mean over folds. Scaled metrics follow Hyndman & Koehler (2006): each series' errors are divided by that series' own training-window naive error, then averaged over series (here weighted by scored points, our choice). Unscaled metrics are pooled across series, so on a panel they are dominated by the large-scale series; use a scaled metric to compare series of different scale.

When the feature set includes Exogenous columns, they are sliced from the held-out data automatically (they are "known" in a backtest). A backtest uses the realised values of the covariates, so it scores ex-post forecasts (Hyndman & Athanasopoulos 2021, §7.6). For covariates not known at the origin (a competitor's price, the weather) this typically understates the error of the real, ex-ante forecast, which also carries the error of forecasting the covariate. For covariates known in advance (calendar effects, planned promotions, prices you set) ex-ante and ex-post agree. To measure ex-ante error, supply in the held-out rows the covariate values that were available at the origin (a forecast, or a lagged column).

Example

results = backtest(fc, df; horizon=28, initial=730, step=28,
                   metrics=(mae, rmse, smape))
results.metrics   # per-fold and overall scores
source
MachineLearningForecast.BacktestResult — Type
BacktestResult

Result of backtest. Both fields are columntables (NamedTuples of vectors, Tables.jl-compatible):

  • folds: one row per fold × horizon step, with columns :fold, :origin (the last training timestamp the row's forecast starts from), :step (1..horizon), the spec's time column, :y (actual), and :y_hat (forecast). A panel backtest adds the id column after :step.
  • metrics: one row per fold × metric (columns :fold, :origin, :metric, :value), plus one overall summary row per metric with fold=0 (:value is the mean of the per-fold values, :origin is missing). A fold's :origin is missing when its series start their forecasts at different timestamps.

Example

results.folds.y_hat   # every forecast, fold by fold
results.metrics       # per-fold and overall scores

MachineLearningForecast.mase — Function
mase(y, ŷ; y_train, m=1) -> Float64

Mean absolute scaled error: mae(y, ŷ) divided by the in-sample MAE of the (seasonal) naive forecast with seasonality m on y_train (mean(|y_train[t] - y_train[t-m]|)). A value below 1 means the errors are smaller on average than the in-sample one-step (lag-m) naive errors (Hyndman & Koehler 2006); multi-step errors are naturally larger, so compare with a naive baseline backtested at the same horizon. On intermittent series (many zeros), MAE-based measures, including MASE, can favour forecasts close to zero; the M5 competition used a squared-error scaled measure (RMSSE) for this reason (Makridakis, Spiliotis & Assimakopoulos 2022); use rmsse for such series. If the naive error is zero (constant training series), a warning is emitted and Inf is returned. One series with a constant training window makes that fold's score, and so the overall score, Inf.

Example

mase([10.0, 12.0], [11.0, 11.0]; y_train=[1.0, 3.0, 1.0, 3.0])   # 0.5
source
MachineLearningForecast.rmsse — Function
rmsse(y, ŷ; y_train, m=1) -> Float64

Root mean squared scaled error: rmse(y, ŷ) divided by the root of the in-sample mean squared error of the (seasonal) naive forecast with seasonality m on y_train,

rmse(y, ŷ) / sqrt(mean((y_train[t] - y_train[t-m])²))

the scale being taken over the whole training window. It is the RMSSE of the M5 competition (Makridakis, Spiliotis & Assimakopoulos 2022), except that M5 computes the scale only from the first non-zero value on, and its seasonal form for any m (Hyndman & Athanasopoulos 2021, §5.8); Hyndman & Koehler (2006) suggest the in-sample RMSE of the naive method as the denominator of a scaled RMSE. A value below 1 means the errors are smaller than the in-sample one-step (lag-m) naive errors; multi-step errors are naturally larger, so compare with a naive baseline backtested at the same horizon.

On a single series, RMSSE ranks methods exactly as rmse does, since the scale is the same for all of them (Koutsandreas et al. 2022); the scale matters when comparing series. Squared errors suit intermittent series (many zeros), where absolute errors favour forecasts close to zero (Makridakis, Spiliotis & Assimakopoulos 2022; Hewamalage, Ackermann & Bergmeir 2023). The price is that RMSSE is more sensitive to outliers than mase (Hyndman & Koehler 2006; Hewamalage, Ackermann & Bergmeir 2023). If the naive error is zero (constant training series), a warning is emitted and Inf is returned.

In backtest it is computed per series, aggregated across series weighted by scored points, then averaged over folds. This is not the dollar-weighted WRMSSE of M5. One series with a constant training window makes that fold's score, and so the overall score, Inf.

Example

rmsse([10.0, 14.0], [11.0, 11.0]; y_train=[1.0, 2.0, 4.0, 7.0])   # ≈ 1.035

needs_ytrain(metric) -> Bool

Trait declaring that metric needs the fold's training target in addition to the actuals and forecasts. backtest calls such metrics as metric(y, ŷ; y_train=...) and ordinary ones as metric(y, ŷ). On a panel it calls them once per series, with that series' own training values.

Tuning

MachineLearningForecast.tune — Function
tune(fc::Forecaster, data; grid=nothing, tuner=GridSearch(), max_evals=nothing,
     horizon, initial=nothing, windows=nothing, step=horizon,
     metric=smape) -> TuneResult

Tune the whole forecasting pipeline on backtest score. Each candidate is a NamedTuple of Forecaster field overrides (e.g. model, features, strategy); the candidate spec is rebuilt from fc with those overrides, backtested with backtest(spec, data; horizon, initial, step, metrics=(metric,)), or with windows in place of initial, and scored by the mean of metric across folds (lower is better). Pass exactly one of initial and windows; windows counts each series' folds back from its own end (see backtest for the caveat when the series are not aligned in calendar time).

  • grid: NamedTuple mapping Forecaster field names (model, features, strategy, transform) to candidate value lists. Required for the batch strategies (GridSearch, the Cartesian product; RandomSearch, n uniform draws). A sequential user-defined TuningStrategy owns its own space and may ignore it. Before any fit, tune throws an ArgumentError if a batch candidate it will evaluate has a :strategy that is not a strategy, such as :recursive.
  • max_evals: optional evaluation budget; the loop stops after this many candidates even if the strategy proposes more.
  • Candidate failures never abort the search: the error is caught, the score recorded as missing (and reported to the strategy via tell!), the message stored in the result table's :error column, and the candidate excluded from ranking. A non-finite mean score (NaN or Inf) counts as a failure. If every candidate fails, tune throws an ArgumentError listing the first five candidates with their overrides, the first error in full and the first line of each other error, then the number left out.

Returns a TuneResult with the score table, the best spec, and the best spec refit on all of data. Ties are broken by first-seen order.

Example

using EvoTrees
result = tune(fc, df;
    grid = (model    = [EvoTreeRegressor(eta=0.05), EvoTreeRegressor(eta=0.1)],
            features = [FeatureSet(Lag(1), Lag(7)),
                        FeatureSet(Lag(1), Lag(7), Fourier(365.25, 3))]),
    horizon=28, initial=730, step=28, metric=smape)
result.best_fitted   # ready to forecast
source
MachineLearningForecast.TuneResult — Type
TuneResult

Result of tune:

  • table: a columntable (NamedTuple of vectors) with one row per evaluated candidate — the overridden parameters (one column per key), :mean_score and :std_score (the mean and standard deviation of the metric across backtest folds; std_score is missing with a single fold), and :error (the error message if the candidate failed, missing otherwise). Failed candidates are excluded from ranking.
  • best::Forecaster: the best candidate spec (NOT fitted).
  • best_fitted::FittedForecaster: the best spec refit on ALL of the data.

MachineLearningForecast.TuningStrategy — Type
TuningStrategy

Abstract supertype of tuning search strategies for tune. Shipped strategies: GridSearch and RandomSearch.

tune is an ask!/tell! loop: it asks the strategy for the next candidate, scores it with backtest and tells the strategy the score. The batch strategies serve a precomputed candidate list through this loop; a sequential strategy, such as a Bayesian optimizer defined outside this package, drives it directly.

Extending with your own (sequential) strategy

Subtype TuningStrategy and implement two methods; tune will drive them in an ask!/tell! loop. The two functions are public but not exported, so import them first: import MachineLearningForecast: ask!, tell!.

  • ask!(s::MyStrategy) -> Union{NamedTuple,Nothing} — return the next candidate: a NamedTuple of Forecaster field overrides (keys among :model, :features, :strategy, :transform), drawn from your search space. Return nothing to signal termination.
  • tell!(s::MyStrategy, candidate, score) — receive the result of evaluating candidate: a Float64 backtest score (lower is better), or missing if the candidate failed to evaluate.

Termination is signalled either by ask! returning nothing, or by the max_evals budget enforced by tune. Your strategy owns its search-space representation (construct it with whatever space description it needs).

Example

import MachineLearningForecast: ask!, tell!

mutable struct FirstK <: TuningStrategy
    candidates::Vector{NamedTuple}
    i::Int
end
ask!(s::FirstK) = s.i > length(s.candidates) ? nothing :
                  (c = s.candidates[s.i]; s.i += 1; c)
tell!(s::FirstK, candidate, score) = nothing

Ask a TuningStrategy for its next candidate: a NamedTuple of Forecaster field overrides (keys among :model, :features, :strategy, :transform). Return nothing to signal that the search is finished. MachineLearningForecast.tell! — Function
tell!(strategy, candidate, score)

Report an evaluation result back to a TuningStrategy: candidate is the NamedTuple previously returned by ask!, and score is the Float64 mean backtest metric (lower is better) or missing if the candidate failed to evaluate. Part of the public tuning-extension API: implement it for your own strategy subtypes; see TuningStrategy for the full contract. It is not exported, so import it: import MachineLearningForecast: ask!, tell!.

Example

import MachineLearningForecast: ask!, tell!

mutable struct Logged <: TuningStrategy
    candidates::Vector{NamedTuple}
    scores::Vector{Union{Missing,Float64}}
end
ask!(s::Logged) = length(s.scores) < length(s.candidates) ?
                  s.candidates[length(s.scores) + 1] : nothing
tell!(s::Logged, candidate, score) = push!(s.scores, score)

s.scores   # each candidate's mean backtest score, or missing if it failed
